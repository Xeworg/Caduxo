# FEFO policy bug — separate branch follow-up

Branch: parking; will be picked up after `feat/scanner-first-inventory` (PR #31) merges.

## Problem

The Scanner "FEFO lot selection" setting in the Configuration tab exposes three options, but only two of them work and the third renders empty panels. The user observed "all three options do the same thing".

## Investigation (read-only) findings

Recorded by `gentle-ai-explore` on branch `feat/scanner-first-inventory` after PR #31 was opened. No source files were modified by the investigation.

### Per-policy behavior — `product_match` with ≥2 active lots

| Policy | Pre-selected lot | Picker visible | Picker editable | Venta confirm enables | Visible affordances |
| --- | --- | --- | --- | --- | --- |
| `suggest_fefo` | `lots[0]` (FEFO) | yes | yes | yes once location+qty valid | enabled picker; no extra hint |
| `require_fefo` | `lots[0]` (FEFO) | yes | **no** | yes once location+qty valid | disabled picker + red-style `fefoRequiredNotice` below |
| `manual_lot_choice` | `""` | **NO (bug)** | n/a | n/a | **empty panel** — no product line, no picker, no location/qty/confirm |

For `lot_match` (any policy, FEFO bypassed): the compact resolved-summary shows the scanned lot with `selectedLotHint` ("Resolved by lot code — FEFO bypassed…") and the full Sale/Stock-out form; no picker is shown.

### Confirmed bug: `manual_lot_choice` empty panel

1. `applyResolveResult` sets `selectedLotId = ""` (`src/components/ScannerPage.svelte:815`) when `fefoPolicy === "manual_lot_choice"`.
2. `resolvedLot` derivation returns `null` in that case (`ScannerPage.svelte:238-240`).
3. Venta panel main branch gates on `resolved && activeProduct && resolvedLot` (`ScannerPage.svelte:1430`); the panel falls through with no fallback match.
4. Stock-out panel has the identical defect at `ScannerPage.svelte:1639`.

### Subtle UX issue: `suggest_fefo` vs `require_fefo`

Same preselect, same source="fefo" resolved lot, same form. Visible delta is limited to:
- `disabled={lotPickerDisabled}` on the Listbox (`src/components/ScannerPage.svelte:1446`).
- One-line `fefoRequiredNotice` hint visible only when `require_fefo`.

Easy to miss if the user agrees with FEFO and never opens the dropdown.

## Recommended fix

Loosen the Venta and Stock-out panel main gates at `ScannerPage.svelte:1430` and `:1639` from
```
{:else if resolved && activeProduct && resolvedLot}
```
to
```
{:else if resolved && activeProduct && (resolvedLot || (resolved.match_type === "product_match" && resolved.lots.length > 0))}
```
so the picker-first branch renders whenever a `product_match` produced at least one lot, even before the user picks. Continue to gate `canConfirmSale` / `canConfirmStockOut` on the existing `resolvedLot` check so the confirm button stays disabled until a lot is selected.

Reuse existing translations:
- `scanner.sale.invalid.lot` for the "pick a lot to continue" alert (`src/i18n/en/index.ts:1122`, `src/i18n/es/index.ts:1124`).
- `scanner.stockOut.invalid.lot` for the Stock-out variant (`en/index.ts:1174`, `es/index.ts:1176`).

Optional UX widening: add one short string per locale to differentiate `suggest_fefo` from `require_fefo` (e.g. "FEFO pre-selected — change if needed" under `suggest_fefo`, leaving the existing red-style notice for `require_fefo`). Adds one new i18n key pair (≤11 chars × 2 locales).

## Risks and constraints

- Backend (`src-tauri/`): no FEFO conditioning; fix is **purely client-side**. No IPC, schema, or migration changes.
- i18n: minimal fix needs no new keys; widening requires one new pair.
- `i18n-types.ts`: regenerated by `paraglide` automatically; only required if a new key is added.
- Tests: no Svelte component harness exists in this repo. Backend tests at `src-tauri/src/db/repositories/settings.rs:441-501` continue to apply; they exercise the snapshot DTO and do not need to change.
- State: `applyResolveResult` already sets `selectedLotId = ""` correctly under `manual_lot_choice` (`:815`); no further mutation is required at the resolve boundary.
